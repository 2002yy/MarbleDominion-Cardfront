## 1. 项目定位

《领土战争》当前不是复刻某个已发行作品，而是围绕以下结构持续迭代的 Godot 4.x 可玩原型：

```text
中央方形领土战场
+ 四角炮台
+ 四个外部独立控制仓
+ 宏观事件转盘系统
```

项目长期方向不是纯程序原型，而是逐步升级为：

```text
卡通竞技实验室风
+ 综艺 / 电竞比赛式 HUD
+ 机械控制仓
+ 高辨识度阵营配色
+ 可见、可演出的全局随机事件
```

## 2. 当前开发原则

后续开发必须遵守这些原则：

```text
不要从零重建项目
必须基于现有 BallWar 工程继续修改
核心玩法优先于花哨表现
随机必须可见，但不能破坏控制仓核心
大地图可读性优先于额外装饰物
```

## 3. 当前不变的核心玩法

以下规则是项目主干，后续 UI、美术、事件系统都不能破坏：

1. 玩家不直接控制炮台、子弹或控制球。
2. 炮台是否发射、发射多少，完全由各自控制仓结果决定。
3. 控制球进入倍率口时，修改当前 `pending_count`。
4. 控制球进入发射口时，触发对应炮台按当前 `pending_count` 连续发射。
5. 发射期间控制仓锁定，不继续下落，也不能继续加球。
6. 发射完成后，只重置进入发射口的那一颗控制球，其他控制球保留当前位置。
7. 子弹按“一发影响一个格子”的规则扩张领土。
8. 子弹遇到异色格后占领并消失，遇到同色格继续飞行。
9. 炮台保持优雅的内部摆动，不因发射中断。
10. 炮台血量归零后停止发射，对应控制仓进入损坏状态。

## 5. 视觉与产品方向

长期视觉风格保持：

```text
卡通
竞技
实验室
桌游机械装置
轻未来感
```

整体表现要求：

- 高饱和阵营色 + 深色背景 + 柔和发光
- UI 不是网页控件感，而是游戏节目感 / 综艺装置感
- 控制仓要像玩具机械控制台，而不是程序白板
- 顶部 HUD 要像电竞赛事信息条，而不是普通文本栏

## 6. 已确认的 UI / 美术升级方向

### 6.1 阵营能量按钮

`+球` 按钮继续沿用“阵营能量按钮 / 悬浮芯片按钮”方向：

- 阵营色底
- 深色外框
- 柔和发光边
- 有浮起感
- 保留 `+球` 文字
- 可加小球图标

状态至少区分：

```text
普通
悬停
按下
禁用
```

### 6.2 控制仓状态视觉

控制仓至少区分三态：

```text
普通
锁定
损坏
```

锁定状态不再依赖“锁定中/待发射”纯文字，应以视觉表达为主：

- 底部门口灰化
- 半透明金属挡板
- 斜纹 / 警示纹
- 中央大数字显示剩余发射数
- 可附加 BUSY 灯条 / 锁头 / 输送感

## 7. 性能与工程约束

旧性能附录继续有效，后续开发不得随意删除现有保护机制。

当前必须继续保留和遵守：

- 低 / 中 / 高画质档位
- 活跃子弹上限控制
- 子弹拖尾点数分级
- `simple_draw` 高压兜底
- 战场整图重绘风险意识

继续开发时的工程要求：

1. 尽量避免 Godot warning。
2. 注意 enum cast、整数除法、Variant 推断、未使用参数。
3. 每次交付都要检查 `20x20 / 30x30 / 40x40 / 50x50` 四档。
4. 新增表现层不得明显破坏 FPS 和战场可读性。

## 8. 事件转盘系统定位

事件转盘是全局随机事件系统，不直接控制炮台，而是干预某一阵营的控制仓状态。

核心原则：

```text
不直接让炮台开火
不绕过控制仓
随机性必须可见
事件结果要能影响 pending_count、控制球、控制仓状态
```

设计分层：

```text
控制仓 = 微观随机
事件转盘 = 宏观随机
```

## 9. 事件系统与控制仓关系

“本次”的定义：

```text
本次 = 目标控制仓当前的 pending_count
```

例如：

```text
pending_count = 16
本次 +10 => 26
本次 x2  => 32
本次 x3  => 48
```

所有结果受当前模式单次发射上限限制：

| 模式 | 单次发射上限 |
| --- | ---: |
| 基础模式 | 2048 |
| 占领模式 | 2048 |
| 限时模式 | 2048 |
| 狂野模式 | 2187 |

锁定中处理规则：

```text
控制仓未锁定：事件立即作用
控制仓锁定中：正向 pending_count 类事件转为“下一轮生效”
控制仓干扰类事件立即生效
```

## 10. 第一版事件效果池

第一版六个效果全部等概率：

```text
重转
本次 +10
本次 x2
本次 x3
加 1 球进控制仓
控制仓干扰
```

### 10.1 重转

- 只重转效果，不重转颜色
- 最多连续重转 2 次
- 超过后强制变成 `本次 +10`

### 10.2 本次 +10

```text
pending_count += 10
```

### 10.3 本次 x2

```text
pending_count *= 2
```

### 10.4 本次 x3

```text
pending_count *= 3
```

### 10.5 加 1 球进控制仓

```text
控制仓未满：直接 +1 控制球
控制仓已满：转化为 pending_count +10
```

### 10.6 控制仓干扰

规则：

```text
持续 5 秒
x2 / x3 / 发射口全部关闭
控制球不能落入任何口
控制球到底后被弹回或重新抛起
期间不能触发倍率与发射
```

若当前正在发射：

```text
取消当前剩余发射
控制仓立即解除发射锁定
pending_count 回退为 max(1, floor(剩余发射数 * 0.25))
再进入 5 秒干扰状态
```

## 11. 颜色轮盘公平机制

颜色轮盘不是四方均分，而是按局势做权重修正。

基础排名权重：

| 当前排名 | 权重 |
| --- | ---: |
| 第一名 | 0.8 |
| 第二名 | 1.0 |
| 第三名 | 1.15 |
| 第四名 | 1.3 |

事件类型修正：

- 正面事件：偏向落后阵营
- 负面事件：偏向领先阵营
- 中性事件：四方均等

## 12. 各模式事件频率

### 基础模式

```text
开局 60 秒后开始
每 60 秒一次
```

### 占领模式

```text
开局 30 秒后开始
每 40 秒一次
最高占领率 >= 65% 后缩短为 30 秒
```

### 限时模式

按剩余时间判断：

```text
开局 30 秒后开始
剩余时间 > 120 秒：每 45 秒
60 秒 < 剩余时间 <= 120 秒：每 30 秒
剩余时间 <= 60 秒：每 20 秒
```

### 狂野模式

```text
开局 20 秒后开始
每 20~30 秒一次
```

## 13. 事件转盘 UI 定位

这一条现已明确：

```text
不把物理转盘常驻放在中央战场中心线
不侵占中央主战场可读区域
事件转盘采用“顶部中轴下拉式综艺转盘”
逻辑先定结果
动画再模拟物理停靠
```

### 13.1 推荐放置方式

物理转盘作为临时舞台出现，不常驻。

流程：

```text
平时：
只保留右下角“下次事件倒计时”

触发时：
顶部中央的事件舞台从 HUD 下方滑下
停在顶部占领条下方、主战场上方
先转颜色轮盘
再转效果轮盘
显示结果
随后收回顶部
```

这样做的原因：

- 不侵占中央战场核心观察区
- 在大地图下依然稳
- 更有“综艺节目装置”感
- 最容易和现有顶部 HUD 体系整合

### 13.2 底层实现原则

推荐实现：

```text
先按权重抽出结果
再让轮盘动画停到这个结果
```

玩家看到的是：

```text
转盘加速
高速旋转
逐渐减速
指针咔咔跳格
最终停在红方 / x3
```

这属于“物理感实现”，但不是把结果完全交给实时物理模拟。

这样更适合当前游戏开发，因为它同时满足：

- 结果可控
- 权重逻辑稳定
- 演出感足够强
- 不会因为真实物理误差破坏平衡

动画原则补充：

```text
不要直接匀速转
必须有惯性
```

建议表现为：

- 起转阶段有明显加速
- 中段保持高速旋转
- 末段逐渐减速
- 临近目标格时出现指针跳格 / 咔哒感
- 最终停靠到预先确定的目标结果

### 13.3 为什么不放中心线

对 `30x30 / 40x40 / 50x50` 来说，中央区域已经主要服务于：

- 观察领土变化
- 观察子弹扩张路线
- 观察四角战局均衡

如果常驻一个实体转盘，会直接抢掉最宝贵的视觉空间。

### 13.4 两段式转盘布局

不建议做一个超大单圆盘，而是采用：

```text
左：颜色轮盘
右：效果轮盘
```

流程：

```text
颜色轮盘先转
停下：红方
效果轮盘再转
停下：本次 x3
弹出：红方：本次 x3！
```

这样比一个巨大圆盘更省空间，也更适合顶部中轴舞台。

尺寸建议：

| 地图尺寸 | 轮盘显示方式 |
| --- | --- |
| 10×10 / 20×20 | 可显示大浮层，轮盘直径 160–180 |
| 30×30 | 中等浮层，轮盘直径 130–150 |
| 40×40 / 50×50 / 60×60 | 紧凑浮层，轮盘直径 100–130 |

原则：

```text
大地图不要追求大圆盘
而是追求清楚可见
```

### 13.5 第一版预留位

第一版即使先不做复杂贴图轮盘，也要在结构上预留：

- 顶部中央事件舞台容器
- 下拉动画位
- 左侧颜色轮盘显示区
- 右侧效果轮盘显示区
- 结果停驻区
- 收回动画位

## 14. 事件转盘节奏时长修订

之前“约 2 秒转完”的节奏太短，不利于玩家看清结果，也不够综艺化。

当前建议改为更从容的一版：

```text
舞台滑下：0.35 秒
颜色轮盘加速 + 高速 + 减速：1.20 秒
阵营停顿确认：0.20 秒
效果轮盘加速 + 高速 + 减速：1.40 秒
效果停顿确认：0.25 秒
结果停驻展示：1.60 秒
中央横幅补充显示：2.20 秒
舞台收回：0.35 秒
```

说明：

- 玩家实际可见的整段事件表演约 5 到 6 秒
- 中央横幅可以和舞台停驻部分重叠
- 这样既能看清“先选阵营、再选效果”，又不会拖太久
- 两个轮盘都应表现出“指针跳格感”和“末端减速停靠感”

## 15. 事件期间是否暂停游戏

第一版建议：

```text
不暂停游戏
```

原因：

- 事件转盘本身就是战局的一部分
- 游戏继续运行更有现场感
- 更符合“综艺比赛中插入突发事件”的氛围

第一版交互原则：

```text
转盘浮层不挡交互
mouse_filter = MOUSE_FILTER_IGNORE
```

这样玩家在事件演出期间仍然可以：

- 点 `+球`
- 点暂停
- 点退出

后续如果现场感太乱，再考虑：

```text
抽奖时短暂慢动作
而不是完全暂停
```

## 16. 事件系统 HUD

平时右下角显示：

```text
事件：最近一次结果
下次事件：00:28
```

转盘激活时：

- 右下角仍可继续显示倒计时 / 当前事件状态

## 17. 代码结构建议

后续实现时，不要把事件系统直接塞进 `Main.gd`。

建议拆成：

```text
EventRouletteController.gd
EventRouletteView.gd
```

职责分离：

### EventRouletteController.gd

负责：

- 事件计时
- 根据模式决定触发间隔
- 按权重抽阵营
- 抽效果
- 先确定最终结果
- 应用事件结果
- 管理重转逻辑
- 处理锁定中转下一轮
- 存档状态读写

### EventRouletteView.gd

负责：

- 顶部中轴下拉式事件舞台
- 左右双轮盘显示
- 转盘旋转动画
- 惯性节奏
- 停格表现
- 指针跳格感
- 结果文字提示
- 收回动画
- 浮层 `mouse_filter = MOUSE_FILTER_IGNORE`
- 和中央横幅的表现层衔接

### Main.gd

只负责：

- 创建控制器和视图
- 传入引用
- 接收少量回调
- 保持与现有 HUD / 存档 / 场景生命周期对接
